## How to use this file

1. Copy `orbit-system.html`, `setup-orbit.sh` and this file into your repo root.
2. `git add -A && git commit -m "docs: ORBIT design system"`
3. `chmod +x setup-orbit.sh && ./setup-orbit.sh`
   It extracts the tokens and component CSS out of the HTML byte-for-byte and writes
   `CLAUDE.md`. It writes no Blade, PHP or JS — that is Claude Code's job.
4. Add the four `@import` lines it prints to `resources/css/app.css`, then commit.
5. Open Claude Code and paste **Session 1** from `KICKOFF-PROMPT.txt`.
6. One session at a time. Review and merge before starting the next.

**Why a script rather than letting the agent copy the CSS:** 72 design tokens and 140
component classes across 256 rules. An agent retyping that will introduce silent errors,
and every wrong hex quietly breaks a verified contrast guarantee. The CSS is mechanical,
so a script does it exactly. Everything requiring judgement — the Blade components, the
screens, the data model — is left to Claude Code.

**Never open with "redesign my app to look like this."** That produces one beautiful
screen and forty broken ones. Every instruction here is bottom-up on purpose: tokens
first, screens last, so the app improves at every step and is never half-converted.

## Context

### What the product is
Elite Event Hub manages large events end to end: a portfolio Command Center across all
events, then per-event modules. Reference event: *The First World Public Summit*,
Nov 8–12 2026, St. Regis Amman, 650 participants, JD 350,000 budget.

**All 25 modules that must be converted:**

| Level | Modules |
|---|---|
| Portfolio | Command Center, Events, Projects, Tasks, Finance, Sponsors, Reports, Settings |
| Event core | Overview, Planning, Tasks, Agenda |
| Money | Budget, Approvals, Risks |
| Physical | Venue, Exhibition, Transport, Accommodation |
| People | Speakers, Attendees, Suppliers, Sponsors |
| Documents | Event Brief, Contract, Documents, Reports |
| System | Settings, AI |

Plus the cross-cutting work that is not a module: auth, global chrome, empty states,
error and loading states, print/PDF, email templates, and responsive. Session 6 of the
kickoff file covers all of it.

### What is wrong with the current UI
- **Gold is used on everything** — buttons, borders, rings, headings, icons — so nothing
  reads as more important than anything else.
- **Every card has the same visual weight.** Nine equal boxes give no entry point.
- **The module rail is a flat list of 20 items**, scanned in full on every visit.
- **Dark chrome sits on a light body** with no bridge; the header reads as a banner.
- **Numbers are set in the UI typeface**, so currency columns don't align.
- **Donut charts with legends** are used for simple two- and three-value splits.

### The five laws

| # | Law | What it means in code |
|---|---|---|
| 1 | One light source | Gold appears on exactly three things per viewport: the primary action, the current position, the single most important number. |
| 2 | Distance is relevance | Modules orbit the event core. Inner arc = 5 touched daily. Outer arc = structure, smaller. |
| 3 | Light is home | Light is the default surface. Dark is a mode entered for show days. Chrome stays dark in both. |
| 4 | Numbers are typography | Every figure in JetBrains Mono with tabular numerals. |
| 5 | Stillness is a feature | Two looping animations exist in the whole system: overdue pulse, live-phase breathe. |

## Design tokens

Generated by `setup-orbit.sh` into `resources/css/orbit-tokens.css`. **Never edit that
file.** If a token must change, change the HTML and re-run the script.

Structure:
- `:root, [data-theme="light"]` — the light palette (default)
- `[data-theme="dark"]` — the dark palette, **identical variable names**
- `:root` — shared: fonts, spacing, radii, easing, durations

Light is the default. Switch by setting `data-theme="dark"` on `<html>`.
Because both themes define the same names, no component needs a dark variant.

### THE TWO GOLDS — read this twice

| Token | Value | Job | Never |
|---|---|---|---|
| `--gold` | `#8A6209` | text, icons, labels — 5.48:1 on white | as a fill behind dark text |
| `--gold-lit` | `#E8B84B` | fills, rings, active states, dock highlight — carries dark text at 9.16:1 | **as text on a light surface — 1.69:1** |

Every signal colour follows the same pattern: `--vital` reads, `--vital-lit`
fills. Same for ion, plasma, flare and critical. Getting this backwards is the
single most likely mistake, and it produces text nobody can read.

### Chrome is constant

`--chrome`, `--chrome-2`, `--chrome-ink` are the dark furniture: the KPI strip,
the bottom dock and the Command Center disc. They do **not** change with the
theme. Fixed elements that re-colour on switch make the product feel unstable.

### Palette

| Family | Tokens | Rule |
|---|---|---|
| Surfaces | `--void --abyss --hull --plate --deck` | Five levels. Never a sixth. |
| Borders | `--rim --rim-hi` | Hairline, one step of contrast. |
| Ink | `--ink --ink-2 --ink-3 --ink-4` | Headings, body, meta, placeholders. |
| Gold | `--gold --gold-lit --gold-2 --gold-3 --gold-tint --gold-glow --gold-ink` | The only accent. Scarce by contract. |
| Signal | `--vital --ion --plasma --flare --critical` each with `-lit` and `-tint` | State only, never decoration. |
| Chrome | `--chrome --chrome-2 --chrome-rim --chrome-ink --chrome-ink-2 --chrome-ink-3` | Dark furniture. Constant across themes. |
| Elevation | `--lift-1 --lift-2 --lift-3` | Three levels. |

### Contrast is already verified — do not "improve" the colours
27 text/surface pairs measured per theme. Lowest in light is 4.91:1, lowest in dark is
4.76:1 — every colour that carries meaning clears AA. Dark text on `--gold-lit` is
9.16:1; white on `--chrome` is 16.89:1. If a colour looks wrong to you, raise it with
the owner instead of adjusting it.

### Status colour must be decided server-side, once

```php
// app/Support/Tone.php
enum Tone: string
{
    case Gold     = 'gold';      // the current position / VIP / the one key number
    case Vital    = 'vital';     // done, healthy, paid, confirmed, ready
    case Ion      = 'ion';       // in progress, informational
    case Plasma   = 'plasma';    // planned, upcoming
    case Flare    = 'flare';     // pending, needs approval, watch
    case Critical = 'critical';  // overdue, at risk, over budget
    case Neutral  = 'neutral';   // draft, archived, not started

    public static function forHealth(int $percent): self
    {
        return match (true) {
            $percent >= 85 => self::Vital,
            $percent >= 70 => self::Ion,
            $percent >= 60 => self::Flare,
            default        => self::Critical,
        };
    }

    public static function forTask(string $status, bool $overdue = false): self
    {
        if ($overdue) return self::Critical;

        return match ($status) {
            'done', 'completed', 'approved' => self::Vital,
            'in_progress'                   => self::Ion,
            'planned', 'upcoming'           => self::Plasma,
            'need_approval', 'pending'      => self::Flare,
            'cancelled', 'draft'            => self::Neutral,
            default                         => self::Ion,
        };
    }

    /** Positive variance means under budget. */
    public static function forVariance(float $variance): self
    {
        return match (true) {
            $variance > 0  => self::Vital,
            $variance == 0 => self::Neutral,
            default        => self::Critical,
        };
    }
}
```

**No Blade template may contain a colour literal.** If a view needs a colour, it asks
`Tone` for one.

### Theme policy — dark by default, light for documents

```php
// app/Support/ThemePolicy.php
class ThemePolicy
{
    /** Change the product-wide default here and nowhere else. */
    protected const DEFAULT_THEME = 'light';

    /** Live operations. Everything else is light. */
    protected const DARK_MODULES = [
        'pulse', 'run-of-show', 'check-in', 'transport-board', 'twin',
    ];

    public static function for(string $module, ?object $event = null): string
    {
        if (session()->has('theme.override')) {
            return session('theme.override');
        }

        // Show days go dark automatically.
        if ($event?->phase instanceof \App\Enums\Phase && $event->phase->prefersDarkTheme()) {
            return 'dark';
        }

        return in_array($module, self::DARK_MODULES, true)
            ? 'dark'
            : self::DEFAULT_THEME;
    }

    public static function override(string $theme): void
    {
        abort_unless(in_array($theme, ['light', 'dark'], true), 422);
        session(['theme.override' => $theme]);
    }

    public static function clearOverride(): void
    {
        session()->forget('theme.override');
    }
}
```

Users can override for a session from a header control; it clears on logout.
**If you later want the ratio inverted, change `DEFAULT_THEME` and move modules
between the two lists. Nothing else in the codebase changes.**

Roughly 70% of screens land light, 30% dark — that ratio is a consequence of the
module lists, not a hard-coded number.

## Alpine patterns

```js
// resources/js/orbit.js — import before Alpine.start()
document.addEventListener('alpine:init', () => {

  Alpine.store('theme', {
    current: document.documentElement.dataset.theme || 'light',
    set(v) {
      this.current = v;
      document.documentElement.dataset.theme = v;
      fetch('/theme-override', {
        method: 'POST',
        headers: {
          'Content-Type': 'application/json',
          'X-CSRF-TOKEN': document.querySelector('meta[name=csrf-token]')?.content ?? '',
        },
        body: JSON.stringify({ theme: v }),
      });
    },
    toggle() { this.set(this.current === 'dark' ? 'light' : 'dark'); },
  });

  Alpine.data('orbitRing', (value = 0) => ({
    v: 0,
    init() { this.$nextTick(() => { this.v = value; }); },
  }));

  Alpine.data('orbitPalette', () => ({
    open: false,
    init() {
      window.addEventListener('keydown', (e) => {
        if ((e.metaKey || e.ctrlKey) && e.key.toLowerCase() === 'k') {
          e.preventDefault();
          this.open = !this.open;
          if (this.open) this.$nextTick(() => this.$refs.input?.focus());
        }
        if (e.key === 'Escape') this.open = false;
      });
    },
  }));
});

if (window.matchMedia('(prefers-reduced-motion: reduce)').matches) {
  const s = document.createElement('style');
  s.textContent = '*,*::before,*::after{animation:none!important;transition-duration:.01ms!important}';
  document.head.appendChild(s);
}
```

## Phases

One PR per phase, behind a feature flag, with before/after screenshots.

### Phase 0 — Audit (no code changes)
`docs/orbit-migration-plan.md` per Session 1 of the kickoff file.

### Phase 1 — Tokens & type (~2 days)
Token CSS is already generated. Make the rest of the app consume it: replace every
hard-coded value, self-host the fonts, add `data-theme`, create `ThemePolicy` and `Tone`.
**Acceptance:** zero hex colours and zero literal font-sizes in `resources/views/**`.

### Phase 2 — Primitives (~4 days)
Every component in the map, plus the auth-gated `/design` gallery rendering them from
the real Blade source.
**Acceptance:** `/design` renders every component in both themes. No view constructs a
button, badge or card by hand.

### Phase 3 — Navigation (~3 days)
Arc orbit nav, bottom dock, topbar with search and event chip, responsive collapse,
⌘K palette. Retire the 20-item sidebar behind flag `orbit_nav`.
**Acceptance:** every module reachable in ≤2 keystrokes; badge counts from live queries.

### Phase 4 — Screens (~4 weeks)
All 25 modules, sessions 5a–5n of the kickoff file, one per session, in that order.
**Acceptance:** each screen has exactly one hero card; gold appears at most 3 times per
viewport.

### Phase 5 — Cross-cutting and polish (~2 weeks)
Sessions 6a–6g and 7: auth, global chrome, empty states, error and loading states,
print/PDF, email templates, responsive, reduced-motion, contrast CI test, dead CSS removal.

## What to watch for

- **The sidebar retirement is the riskiest change.** Run the two-ring nav behind a flag
  for your own team for a week before clients see it. Track which outer-ring modules get
  expanded most and promote them into the inner ring.
- **Do not let the agent restyle screens in Phase 1 or 2.** It will want to. Bottom-up
  only works if screens come last.
- **The `/design` route is not optional.** Without a living gallery rendered from real
  components, the system drifts within a quarter and you are back where you started.
- **Emails cannot use CSS custom properties.** Generate email templates from the token
  file with hex inlined, so they cannot drift from the app.
- **Data inconsistency already in your app:** Contract shows JD 350,000 collected while
  Budget shows income JD 0, producing a false −JD 214,498 P&L. Resolve it before the
  Budget screen is rebuilt, or the new design will present the wrong number more
  beautifully.
