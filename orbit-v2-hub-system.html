About that 3D view. The image in your mockup is a render — it can't show live capacity, setup progress or issue pins because it's a picture. What you actually need is a plan you can drive from data. 01 · Policy

The 70 / 30 rule

Theme isn't a preference toggle buried in settings — it's a property of the work being done. Each module declares its default; the user can override for a session.

70%

Light — planning & desk work

Daylight offices, long reading sessions, anything that gets printed or PDF'd. Dense tables are easier to scan, and clients see documents the way they'll be exported.

Command CenterEvent HubBudget Event BriefContractVenue SuppliersAttendeesReports SettingsDocumentsSponsors
30%

Dark — live operations

Show days, control rooms, load-in at 5am, on-site tablets in a dim ballroom. Lower emitted light, less eye fatigue over an eleven-hour shift, and status colours read louder.

Event Pulse (live) Run of Show Digital Twin Transport board On-site check-in

Plus: automatic switch to dark once an event enters Event Days phase.

// One rule, enforced in one place. app/Support/ThemePolicy.php class ThemePolicy { protected static array $dark = ['pulse','run-of-show','twin','transport','check-in']; public static function for(string $module, ?Event $event = null): string { if (session()->has('theme.override')) return session('theme.override'); if ($event?->phase === Phase::EventDays) return 'dark'; // show days go dark return in_array($module, static::$dark) ? 'dark' : 'light'; } }
02 · Foundations

Iris & Gold

Two accents with a strict division of labour. Iris is a verb, gold is a noun.

Iris — the working accent

Use for: primary buttons, focus rings, active nav, selected tabs, progress fills, links, AI surfaces, map pins, the "you are here" state.

Active Focus
Gold — prestige only

Use for: the Elite brand mark, VIP and premium tiers, sponsorship gold packages, certificates, and the header of exported PDFs. Never a button, never a focus ring, never a status.

12 · Build

Handing this to Claude Code

A full, paste-ready implementation brief ships alongside this file as CLAUDE-CODE-BRIEF.md. Drop it in your repo root, then start the agent with a single sentence. The short version:

Do this
  • → Put ORBIT-SYSTEM.md and this HTML file in the repo. Point the agent at both.
  • → Have it work bottom-up: tokens → components → nav → screens. Never screen-by-screen.
  • → One PR per phase, behind a feature flag, with before/after screenshots.
  • → Make it write a /design route in your app that renders the component gallery from real Blade components — your living version of this page.
Don't do this
  • → Don't say "redesign my app to look like this." You'll get one beautiful screen and 40 broken ones.
  • → Don't let it invent new colours, radii or shadows. Every value comes from a token.
  • → Don't merge the 3D twin before the zone data model exists. Data first, render second.
  • → Don't skip the /design route. Without it, the system rots in three months.
# The opening message. Everything else is in the brief file. Read CLAUDE-CODE-BRIEF.md and orbit-v2-hub-system.html in the repo root. The HTML is the visual source of truth — open it, read the CSS in <style>, and treat those tokens and class names as the spec. Start with Phase 0 only: audit the codebase and write docs/orbit-migration-plan.md listing every Blade view, every hard-coded colour and font-size, and a file-by-file order of work. Do not change any code yet. Stop when the plan is written.
