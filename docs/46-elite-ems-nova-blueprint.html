Product blueprint · v1 · September 2026

Elite EMS Nova

The operating system for events. Nova is organised around running an event, not around modules. Each event is a live operation with a phase, a health score, a critical path and a team, and every screen serves one question: what does this event need from me now?

For Elite Business Hub leadership, product, design & engineering Markets Jordan · GCC · MENA Languages English (LTR) · العربية (RTL) Base currency JOD, three decimals
How this relates to today's Elite EMS

This is a reinvention on paper. The current codebase is still an asset: 10 state machines, 6 permission gates, 17 print documents, bilingual contracts, token-based registration and check-in, the Arrivals Desk, and 1,137 passing tests all carry over into Nova's domain layer. The roadmap in §22 ships Nova gradually alongside the current app, one surface at a time, rather than as a big-bang rewrite. Two current project rules are consciously set aside here: "don't redesign screens" (because Nova is a new product surface) and "multi-tenant is deferred" (Nova keeps it deferred, but builds the tenant key in from day one).

01 · Product vision

An event is a live operation, not a record

Event software has usually been a filing cabinet: one drawer for suppliers, one for attendees, one for the budget. Planners keep the actual operation in their heads and in WhatsApp, and the software only finds out afterwards. Nova reverses that. The software holds the operation (what has to happen, in what order, who is blocking whom, what it costs and what changed overnight) and people step in where judgement is needed.

Operations, not modules

Nobody "goes to the supplier module". They open the ICFT event, and its production gap is in front of them with the supplier who caused it.

Phase-aware by default

An event in Procurement looks different from one in Live. The Event Space re-orders itself around what that phase needs.

Evidence over opinion

Every score, alert and AI recommendation can be traced to the records behind it. No black boxes, and no number without a definition.

One truth for money

Each financial figure states what it measures, how it's calculated and where it comes from. Dashboard, event and client portal all show the same number.

Calm by design

85% light, 10% navy, 5% gold. Gold is used for one thing only: the one action or event that needs you. Everything else stays quiet.

Bilingual from the start

Arabic RTL is built in from day one, not translated later. Contracts, briefs, badges and the client portal are written for both directions.

North-star metric

Decisions resolved per operator-hour. We track the time from a signal ("the stage supplier missed the rigging drawing") to its resolution (reassigned, chased, accepted) across the company. Supporting metrics: time to first useful action after login (target under 10 seconds), events delivered without a Readiness-gate miss, invoice-to-cash days, and the share of AI recommendations accepted without edits.

What Nova is not

  • Not a project tracker with an event skin: tasks exist, but they hang off deliverables, milestones and the critical path.
  • Not an accounting system: Nova owns event economics (quote → contract → invoice → collection → cost → margin) and hands the ledger to the company's accounting package.
  • Not a chatbot with a CRM: AI is an operations partner with evidence, not a text box in the corner.

Level 3 · Work Surfaces

Six reusable surface types render any object set. Users switch views, not screens: the same deliverables show as a Board, a Timeline (Gantt with dependencies) or a Sheet (bulk editing), and the same booths show as a Canvas (floor plan). A Record opens as a side sheet over the current surface (Linear-style peek) and can be expanded to full page. A Document is any printable output (contract, rooming list, run of show) with a live preview beside its data.

Client Portal: a separate front door, same spine

Clients sign in to portal. and see a filtered Event Space built from the same records, through a disclosure policy rather than hand-made copies:

Clients see

  • Timeline & milestones (client-facing labels)
  • Deliverables awaiting their input
  • Approvals: one-tap approve, or request changes with a comment
  • Budget at client price (quote, contracted, invoiced, paid)
  • Weekly report (AI-drafted, human-approved)
  • Documents flagged "client-shareable"

Clients never see

  • Cost, supplier price, margin, management-fee math
  • Internal notes, comments, @mentions
  • Risk register entries marked internal
  • Supplier identities where "white-label" is set
  • AI recommendations meant for staff

Enforced in the API through field-level disclosure policies, not by hiding things in the UI. See §21.

04 · Navigation architecture

No sidebar. A command bar, a context bar and a palette.

Sidebars exist because modules exist. Nova has spaces and operations, so navigation has three layers:

1 · Command bar (top, 52px)

Workspace switcher · Today · Events · Pipeline · Directory · Money · palette field (⌘K) · Live indicator (appears only when an event is live) · notifications · profile. Frosted glass. It's the only persistent chrome.

2 · Context bar (inside an event)

Event name, phase chip, health ring and the ten areas as a horizontal segmented bar. The current phase's primary area is marked with a gold underline. Areas that aren't relevant to this event type fold into "More".

3 · Command palette (⌘K / Ctrl K)

Universal: open, create, do, ask. It handles the keyboard, and on mobile a long-press on the command bar opens it. It's the fastest way to anything.

05 · Event Space architecture

Ten areas, one operation

An Event Space is one operating environment. Its ten areas are lenses on the same event graph (deliverables, people, commitments, money, schedule), so a change in one shows up everywhere at once. A late stage-drawing deliverable in Production moves the critical path in Plan, raises a risk in Command, and puts a line in the client's weekly report.

Lifecycle phases and gates

Phases are sequential with explicit exit criteria. Readiness is the percentage of the current phase's exit criteria that are met, so it always has a precise, checkable meaning.

Health vs Readiness: defined once, used everywhere

Readiness (0–100%) = exit criteria met ÷ exit criteria in the current phase. It answers "can we move on?"
Health (0–100) = 100 − weighted penalties: schedule slip on the critical path (35%), budget variance vs approved version (25%), open risk exposure, i.e. likelihood × impact (20%), decision latency, meaning approvals pending past their SLA (20%). It answers "is it going well?"
Both show as a single ring and a single bar, in the same place on every screen. Today's app shows readiness three different ways; Nova shows it once.

1 · Command

"Is this event OK, and what's next?"

The event's cockpit. Nothing here is edited directly: every tile is a summary that opens the area that owns it.

Event Health
Ring (0–100) with the four penalty drivers as a horizontal breakdown. Clicking a driver shows the records behind it. Trend sparkline over 14 days.
Readiness
Current phase's exit criteria as a checklist. Unmet criteria show owner, due date and a link. "Advance phase" is only available when all are met, or by manager override with a reason (audited).
Risks
Top 5 by exposure (likelihood × impact, 1–25), each with owner, mitigation, trigger date. Internal vs client-visible flag.
Critical Path
A compact chain of the milestones that determine the event date, with float in days. Any milestone with less than 2 days float is marked. This view doesn't exist anywhere in today's app, and it's the single most valuable addition.
Budget Status
One line: Approved budget · Committed · Actual · Forecast at completion · Variance, each with a definition popover. Links to Commercial.
Upcoming Decisions
Approvals waiting (internal and client), with SLA timers and approve/request-changes inline for whoever holds the gate.
AI Summary
Three sentences, regenerated when material facts change. Each clause cites its evidence. "Last generated 07:02 from 214 records."

2 · Plan

"What are we delivering, by when, and who owns it?"

One work model replaces today's parallel Tasks / Plan items / approvals: Objective → Deliverable → Task, with milestones and dependencies as first-class objects.

Scope
A structured scope statement (in scope, out of scope, assumptions), versioned. Changes after Planning create a change request that shows its cost and schedule impact before approval.
Objectives
2–5 measurable outcomes (e.g. "600 qualified delegates", "3 ministerial speakers"). Intelligence reports against them after the event.
Deliverables
The unit of accountability: owner, due date, acceptance criteria, reviewer, client-visible flag. Status: Not started In progress In review Accepted. "Needs approval" is a gate on a deliverable, not a task status.
Timeline
Gantt with drag-to-reschedule, dependency lines, a "today" rule and the event date as a fixed anchor. Baseline vs current overlay shows slip.
Milestones
Zero-duration checkpoints (e.g. "Agenda frozen", "Print files to vendor"). Phase exit criteria are built from milestones.
Dependencies
Finish-to-start, with lag. Cross-area: "Badge print" depends on "Registration closes" (People) and "Branding approved" (Experience).
Risks
The full register (Command shows the top 5). Each risk can create a mitigation deliverable.
Team Assignments
Event roles (Producer, Commercial lead, Logistics lead, Program lead) plus a load view: hours assigned per person per week against capacity, across all events, so the planner sees overload before assigning.

3 · Program

"What happens on stage, where and when?"
Agenda
Multi-day grid by room (columns) × time (rows), drag to move, conflict detection (speaker double-booked, room over capacity, changeover under 10 minutes). Bilingual session titles.
Tracks
Colour-free by default (named, patterned chips) so they don't compete with status colour.
Sessions
Status: draft → awaiting speaker → in review → confirmed → final. Each session has format, room, AV needs (feeds Production), interpretation needs (feeds Logistics).
Speakers & Moderators
Engagements with People records: bio, headshot, deck due date, travel/hotel (feeds Logistics), fee (feeds Commercial), briefing call.
Venues & Room Allocations
Rooms come from the venue's spaces in the Directory. Allocation shows capacity vs expected attendance per session, with seating layout links (Room Layout canvas).
Run of Show
A cue-level timeline per room, generated from sessions and editable to the second: walk-in music, VO, lights, video roll, mic hand-offs. Locked at Readiness. It becomes the Live Mode's show caller view.

4 · People

"Who is coming, and what does each of them need?"

One people table with roles, not eight separate lists. A person can be both speaker and VIP. Each role adds its own fields and workflows.

Delegates
Registration source, ticket type, status (registered → confirmed → checked-in / no-show / cancelled), badge, dietary needs, session sign-ups.
VIPs
Protocol tier, escort, arrival plan (feeds Logistics), seating, gift, "do not photograph" flag.
Sponsors & Exhibitors
Organisation-level engagements: package, entitlements checklist (logo placements, passes, booth, speaking slot) with delivery proof. Feeds the sponsor delivery report.
Speakers
Mirrors Program, seen from the person's side (everything they're in, need, owe).
Media
Accreditation, embargo, interview requests.
Staff & Volunteers
Shifts, posts, radios, briefing acknowledgement. Staff load feeds Team Capacity.
Bulk power
Sheet view, XLSX import with column mapping and a preview of changes before commit, segment builder ("VIPs arriving 11 Nov without transfer").

6 · Production

"Will every physical thing be there, working, on time?"

A single production schedule: every physical item with spec, quantity, supplier, delivery window, install/strike times and status (specified → quoted → ordered → confirmed → delivered → installed → tested).

AV · LED · Lighting · Sound
Per-room technical riders generated from session needs. Conflicts flagged ("Hall B needs 3 wireless handhelds; 2 ordered").
Printing
Files → proof → approved → printed → delivered, with version control on artwork.
Booths & Equipment
Linked to the Exhibition canvas and Room Layouts. Pulls the equipment list per room.
Logistics Readiness
Load-in/load-out schedule by dock and time slot. The build-day Gantt.
Supplier signal
Each supplier's on-time rate, open issues and response time roll up into their Directory scorecard. This is what powers "which supplier is causing delays?"

9 · Live: Live Event Mode

"What is happening right now, and what's wrong?"

A different interface, on purpose. When an event is live, the command bar shows a pulsing Live indicator and ⇧L switches into it. Live Mode is works offline, runs as a PWA, uses 48px targets, and puts incidents first.

Layout
One column on a phone, three columns on a tablet or ops-room screen (Now · Incidents · Arrivals). No secondary navigation. The screen stays awake (wake lock).
Registration
Live check-in count vs expected, by gate. The walk-in desk is a big search field that reads badge references and names, with Arabic transliteration matching. It's today's Arrivals Desk, promoted.
Speaker Readiness
Each upcoming session: speaker arrived · in green room · mic'd · slides loaded. One tap per state, visible to the show caller.
Session Status
Per room: on time / running +7 min / changeover. Overruns ripple into the next sessions and notify affected speakers and the transport lead.
Production Status
Room tech checks (AV, LED, lighting, sound) as green/amber/red with the responsible technician.
VIP Arrivals
Next VIP movements with ETA from the driver's app. "Arrived" triggers the protocol sequence.
Incident Reports
Two taps to log (category, location, severity), optional photo, auto-assigned by category. Critical incidents page the event lead. Every incident has a timeline and a closure note.
Real-Time Updates
A single feed with filters (All · Mine · Critical), pushed over WebSockets, with a visible "last synced" time and an offline queue that syncs automatically on reconnect.

06 · Today Command architecture

A morning briefing, not a dashboard

Today Command reads top to bottom like an executive briefing. Within 10 seconds a user knows their priorities, risks, deadlines, approvals, cash position and event readiness. It's personalised by role: a CEO, a producer and a finance lead see the same seven blocks, filtered and ranked to their responsibilities.

#BlockQuestion it answersContent & interaction
1Morning BriefWhat changed and what matters?A 3–5 sentence narrative in the user's language, generated at 06:30 local time and refreshed when material facts change. Each clause links to evidence. Below it: "Since yesterday: 4 approvals cleared · 1 new risk · JOD 18,450.000 collected."
2Priority StackWhat should I do first?Up to 7 items ranked by severity × proximity × blast radius. Each item: a verb-first title ("Approve Hall B LED quote"), why it's here, what it blocks, and 1–2 inline actions. Resolving an item removes it with an Undo. "Show ranking" explains the score.
3Event HorizonWhich event needs executive attention?The portfolio as operational objects on a time axis (see below).
4Financial PulseIs cash OK?Five figures, each with a definition card: Collected (month to date) · Receivable due in 30 days · Overdue · Payables due in 30 days · Net 30-day cash position. One sparkline, and the top 3 overdue invoices with "Chase", which drafts a message for a person to send.
5Upcoming OperationsWhat happens in the next 7 days?A day-by-day strip: site visits, deliveries, load-ins, sessions, movements, deadlines. Filterable to "mine".
6Team CapacityWho is overloaded?Per person: assigned hours next 14 days vs capacity, stacked by event. People over 110% are flagged, with "Rebalance" suggesting reassignments (AI, with a reason).
7AI RecommendationsWhat should we do next?2–4 cards, each with Reason · Evidence · Impact · Confidence and actions: Accept (does it or drafts it) · Prepare (drafts for review) · Dismiss (asks for a reason, which the system learns from).

Event Horizon, the visual system

Event Horizon replaces charts, widgets and hexagon islands with one legible object per event. Events are lanes on a shared time axis (today → +120 days). Each event is a capsule spanning its dates, and its left edge carries the "operational object" readout:

Each event object shows

  • Event name and client
  • Days remaining (T−26)
  • Health ring (0–100) and Readiness bar (phase %)
  • Phase chip: Opportunity … Archived
  • Budget status: on / at risk / over (text + icon)
  • Approvals: count waiting, oldest age
  • Risk level: highest open exposure (1–25)

Sorting & attention encoding

  • Default sort is the attention score, not the date: health drop × proximity × money at stake.
  • Events needing executive attention get the one gold marker in the system (a 3px gold edge and "Needs you" label). Shape and text carry state, never colour alone.
  • Critical risk uses the red capsule outline plus a ⚠ glyph.
  • Hover or focus opens a peek card with the AI one-liner and the top 3 open issues.
  • Zoom: 30 / 90 / 365 days. Group by phase, client or producer.
07 · AI architecture

An operations partner that shows its work

  "evidence":   [{"type":"deliverable","id":8812,"label":"LED rig drawing — 6 days late"},
                 {"type":"supplier","id":44,"label":"On-time rate 58% (last 90 days)"}],
  "impact":     {"schedule_days": 3, "cost_jod": "2150.000", "events": ["ICFT 2026"]},
  "confidence": {"level":"medium","score":0.68,"why":"2 of 3 signals strong; supplier quote not yet received"},
  "actions":    [{"verb":"prepare","label":"Draft RFQ to Lumen Arabia"},
                 {"verb":"open","label":"Open Production › LED"}]
}

Confidence is calibrated from signal coverage (how many independent signals agree), data freshness (age of the newest evidence) and historical acceptance of that recommendation type. It's shown as High / Medium / Low with the reason, never as an unexplained percentage.

Models and platform

  • Reasoner: Claude Opus 5 (claude-opus-5) with adaptive thinking for briefings, explanations and forecasts. Structured outputs (output_config.format) enforce the recommendation contract above.
  • Workers: Claude Haiku 4.5 (claude-haiku-4-5) for high-volume classification (incident category, email-to-deliverable matching, document tagging).
  • Prompt caching on the stable system prompt and the event's evidence pack, so repeated questions about the same event are cheap. Message Batches for the nightly per-user briefings (asynchronous, half cost).
  • Tool use: the reasoner calls read-only tools (get_event_health, list_overdue_invoices, supplier_scorecard…) that run under the requesting user's permissions.
  • Handle the refusal stop reason and enable server-side fallbacks, so a declined request degrades to a plain summary rather than an error.

Guardrails

  • Permission-scoped retrieval: the evidence graph is filtered by the user's policies before the model sees anything. The AI can never tell a coordinator what a manager-only record says.
  • Portal redaction: anything drafted for a client passes through the same disclosure policy as the portal API. Margin and cost fields are removed before generation.
  • Human-in-the-loop for anything external (emails, portal posts) or financial (payments, POs). The AI prepares; a person commits.
  • Audit: every AI output stores its prompt version, evidence IDs, model, and the user's decision.
  • Evaluation: a golden set of 200 real historical situations (anonymised) is scored on each prompt change: evidence precision, recommendation usefulness, Arabic output quality.

11 · Mobile experience

The phone is a field instrument

Mobile isn't a shrunken desktop. It's for the four things people do away from a desk: decide, check, log, find.

The approvals inbox with swipe-right to approve and swipe-left to request changes (with a required comment). The evidence is shown before the buttons. Biometric confirmation for financial approvals above a threshold.

Today Command compressed: Morning Brief, top 3 priorities, and your events' health. Push notifications only for items in your Priority Stack. There is no firehose.

Incident in two taps plus a photo, site-visit notes with voice-to-text (typed transcript saved, audio optional), and delivery confirmation with a photo.

Delivered as an installable PWA first (one codebase, offline via service worker, web push). A native wrapper is considered in Q4 only if wake lock, NFC badge scanning or background location prove essential.

12 · Accessibility strategy

WCAG 2.2 AA, in both reading directions

Standards we commit to

  • Contrast: 4.5:1 text, 3:1 UI components and focus indicators, validated for every token pair in both themes by CI.
  • Not by colour alone: every status carries text and an icon or shape. Horizon capsules use outline style plus glyphs.
  • Focus (2.4.11, 2.4.13): a 2px focus ring that is never obscured by the sticky command bar. Scroll padding equals the bar's height.
  • Target size (2.5.8): at least 24×24 everywhere; 44×44 in Live Mode and on mobile.
  • Dragging (2.5.7): every drag (board, timeline, floor plan, agenda) has a keyboard and menu alternative ("Move to…", arrow keys with ⇧ for larger steps).
  • Accessible authentication (3.3.8): passkeys and magic links, no cognitive puzzles. The client portal supports magic links.
  • Redundant entry (3.3.7): data typed once is reused. Speaker travel details flow to Logistics, not re-asked.
  • Consistent help (3.2.6): "Ask" (AI) and the human support contact are in the same place on every screen.
  • Live regions: Priority Stack changes, Live updates and toasts are announced politely. Critical incidents are announced assertively.
  • Reduced motion and forced-colours modes are supported and tested.

Arabic RTL as a first-class direction

  • CSS logical properties only (margin-inline-start, inset-inline-end). A stylelint rule bans physical left/right.
  • Directional icons (arrows, chevrons, progress) mirror. Clocks, media controls, logos and charts' time axes do not. Time flows right-to-left in RTL on Horizon and Timeline.
  • Mixed-direction content (Latin supplier names inside Arabic sentences, phone numbers, JOD amounts) is wrapped with <bdi> and unicode-bidi: isolate.
  • Names are stored in both scripts where known. Search matches across transliterations (محمد ↔ Mohammad/Muhammad).
  • Documents (contracts, briefs) support true bilingual side-by-side layout, and an Arabic-first variant for government clients.
  • Every screen is tested in AR before release. Pseudo-localisation (+35% string length) runs in CI.

2 · Planning to procurement

Producer freezes the scope → budget v1 is submitted → manager approves → phase gate "Scope frozen · budget v1 approved" turns green → Procurement opens. Budget lines marked critical create RFQ deliverables → supplier quotes are compared side by side → PO issued (checked against the budget line) → the supplier confirms through a portal link → the deliverable is accepted.

3 · Change request

The client asks for a second breakout room → a ChangeRequest is logged with scope delta → Nova computes the impact (+JOD 3,400.000 cost, +JOD 4,420.000 price, +2 production items, no critical-path effect) → internal approval → client approval in the portal → a change order is added to the contract and the invoice schedule updates. Everything is linked, so there's no side email trail.

4 · Approval loop (internal and client)

Any deliverable with a gate sends an approval request to the gate holder with an SLA (default 48h). Reminders go out at 50% and 100% of the SLA. At 150% it escalates to the event lead and shows in their Priority Stack. Decisions are captured with comment and version. Every approval shows the evidence it was based on.

5 · Readiness to live to closing

At T−7, Nova opens the go/no-go checklist (run of show locked, rooming final, riders met, VIP plans confirmed) → the event lead signs → on the first session day the event switches to Live and Live Mode activates for staff on shift → incidents and updates stream in → after the last session, Closing opens with final invoice, supplier bill matching, a lessons retro prompt and the post-event report draft.

6 · Collections

Installment due → invoice auto-drafted 7 days before → finance reviews and sends → at 1 day overdue, a chaser is drafted in the client's language for a person to send → payment recorded and allocated → receivable clears → Financial Pulse updates for everyone at once.

18 · Database architecture

PostgreSQL, one schema, audited everything

  • Engine: PostgreSQL 17 (production already targets Postgres per the cutover plan). SQLite stays for local development and tests.
  • Keys: bigint identity internally, ULIDs as public IDs in URLs and the API (so URLs don't reveal volumes, following today's token rationale).
  • Tenancy: tenant_id on every table from day one, plus Postgres row-level security policies (disabled until multi-tenant launches). This follows the "deferred" decision without closing the door.
  • Money: amount_minor bigint + currency char(3) + fx_rate numeric(18,8) locked per document. JOD minor unit = 1/1000.
  • State machines: each state column is paired with a *_transitions table (from, to, actor, reason, at). Phase changes and approvals are fully audited.
  • Activity log: an append-only activity table (subject, verb, actor, diff jsonb), partitioned monthly. It powers the "Since yesterday" brief and AI summaries.
  • Bilingual fields: jsonb translation columns ({"en": "...", "ar": "..."}) for user-authored names and titles, with a generated column for search.
  • Search: Postgres full-text with an Arabic-aware configuration plus a trigram index for fuzzy names. Meilisearch is optional later for the palette at scale.
  • Read models: materialised tables for health, readiness, attention score and money chain, recomputed by queued jobs on domain events. Screens read these, so they never recalculate on page load.
  • AI store: ai_insights + evidence_refs (polymorphic record references) + recommendation_decisions. Nothing that's been shown to a user is deleted.
  • Backups: PITR on managed Postgres, nightly logical dumps, and a quarterly restore drill.

20 · React architecture

Inertia + React for Nova surfaces

Why React here, when today's app is Livewire

Nova's key surfaces (palette, Horizon, timeline, canvases, Live Mode offline, optimistic updates) are client-state-heavy. Livewire remains excellent for forms and settings. The plan: new Nova surfaces ship as Inertia React pages inside the same Laravel app, sharing auth, routes and policies. Existing Livewire screens are replaced one by one. There's no separate SPA and no second backend.

  • Language: TypeScript strict. Types for API payloads are generated from the OpenAPI spec (§21).
  • State: server state in TanStack Query (optimistic mutations + Undo); local UI state in component state; no global store until it's proven necessary.
  • Accessibility primitives: React Aria (keyboard, focus management, RTL-aware) under Nova's own styling. There's no Material or Bootstrap anywhere.
  • Styling: Tailwind v4 (already in the stack) driven by Nova tokens as CSS variables, with logical-property utilities only.
  • Performance: route-level code splitting, virtualised lists over 200 rows, and canvases in their own chunks. Budget: under 200KB JS on Today Command.
  • Offline: Live Mode uses a service worker plus an IndexedDB outbox. Mutations queue with idempotency keys and sync on reconnect.

Conventions

  • REST resources nested by event (/events/{id}/deliverables), plus action endpoints for state changes (POST /deliverables/{id}/approve), so the UI, palette and AI all call the same audited actions.
  • JSON:API-style sparse fieldsets and includes. Cursor pagination. ULIDs in URLs.
  • Money is always {"amount_minor": 16800000, "currency": "JOD", "display": "16,800.000"}. Clients never do their own currency formatting.
  • Metrics endpoints return values with their definition ID, so any client can render the definition card.
  • Idempotency-Key is required on every POST from Live Mode and the palette.
  • Realtime: private channels per event (event.{id}) and per user (user.{id}.priority) over Reverb.
  • AI endpoints: POST /ai/explain, /ai/prepare, /ai/recommendations/{id}/decision, streaming for long drafts.
  • OpenAPI 3.1 spec generated from code, used for typed clients and contract tests.
22 · 12-month roadmap

Ship Nova alongside the current app, one surface at a time

Every quarter ends with something people use every day. The current app keeps running, and its screens are retired as Nova's replacements reach parity.

Q4 2026 · Months 1–3

Foundations & Today

  • Postgres cutover · tenant_id + ULIDs
  • Nova tokens, 20 core components, RTL from day one
  • Inertia React shell, command bar, palette (navigate + query)
  • Metric registry + definition cards; money chain read model
  • Today Command v1 (brief is rule-based), My Work, Approvals inbox

Exit: MD and producers start their day in Today Command; money numbers match across all screens.

Q1 2027 · Months 4–6

Event Space core

  • Phase model + gates; Health & Readiness v1
  • Unified work model: Deliverable → Task, dependencies, critical path
  • Event Space: Command, Plan, Commercial
  • Event Horizon; palette create + act
  • AI v1: Explain + Morning Brief with evidence (Claude)

Exit: two live client events run end to end from Nova's Plan and Commercial areas.

Q2 2027 · Months 7–9

Operations depth & Live

  • Program, People, Logistics, Production areas (migrating agenda, transport, rooming, badges)
  • Live Event Mode PWA, offline, incidents, Reverb realtime
  • Supplier scorecards; change requests with impact
  • AI v2: Detect + Recommend with confidence

Exit: one event's show day run entirely in Live Mode; legacy hub tabs retired.

Q3 2027 · Months 10–12

Client portal & Intelligence

  • Client Portal (timeline, approvals, budgets, reports, docs) with disclosure policies
  • Experience area; Intelligence (retro, compare, sponsor performance)
  • AI v3: Prepare (client weekly, sponsor report) + Forecast (readiness at T−7)
  • Accessibility audit (external) · AR usability study

Exit: clients approve in the portal; legacy app switched to read-only.
